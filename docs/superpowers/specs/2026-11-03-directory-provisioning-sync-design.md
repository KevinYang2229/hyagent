# 使用者目錄自動建立與 Webhook 同步：設計文件

狀態：已核准（2026-11-03）。對外契約的完整內容見 [HANDOFF-DIRECTORY-SYNC.md](../../HANDOFF-DIRECTORY-SYNC.md)，兩者必須保持一致。

標記說明：**（決定）** 是產品負責人已確認的內容；**（設計判斷）** 是撰寫者的決定，審核時可推翻；其餘技術細節留給實作者。

## 1. 背景與目的

HyAgent 串接 OA 等系統時，人員都在後台「使用者目錄」手動逐筆建立，人數多時太耗時。

現有的自動登入能帶入姓名、部門、職稱與公司，但資料只存在 Session 與當次請求，不會進入目錄，因此後台看不到這些人，查詢「別人」（代理人候選、通知收件者）或背景工作也讀不到。

本專案要達成：

1. 員工自動登入成功後，自動建立到使用者目錄。**（決定）**
2. 人員異動時，由外部系統主動發 webhook，HyAgent 被動同步。**（決定）**
3. 提供一份對接文件，讓 OA 團隊可依此修改。**（決定）**

OA 由公司內部團隊開發，可以配合實作。**（決定）**

## 2. 目標與範圍

### 目標

- 開啟功能的租戶，員工第一次登入後就出現在目錄與個人權限中。
- OA 的新增、異動、離職事件能反映到目錄，離職者立即失去存取權。
- OA 可分批推送完整名單，讓員工不必先登入就能在後台設定權限，也能用來校正資料。
- 既有未開啟功能的租戶，行為完全不變。

### 不做

- HyAgent 主動向 OA 拉取資料、Excel 匯入。
- 新增「位階」欄位；位階先以職稱（`jobPostName`）對應。**（決定）**
- 依部門自動建立角色、由 OA 決定 HyAgent 的權限。
- 帳號停用狀態（本期只有存在／移出目錄）。
- 多副本之間的目錄即時同步（見 §9）。

### 不可影響原有自動登入 **（決定）**

這是本專案的硬性要求，與其他需求衝突時以此為優先。

**開關關閉時（所有既有租戶的預設）：** 登入的程式路徑、請求與回應格式、錯誤碼、Session 行為、`getApplicant` 的結果都與現在相同。

**開關開啟時：**

- 登入能否成功、回應內容與速度，都不受目錄影響。目錄或刪除紀錄不可成為拒絕登入的理由。
- 自動建立只在 Session 建立後的背景執行，登入流程不等待結果（§4）。
- 同步端點的流量、錯誤與速率限制都不可影響登入（§5）。

**不動的部分：** `HyAgentAssertionVerifier` 的驗證邏輯、登入的 `aud`、`POST /api/auth/sso/exchange` 的契約，以及現有的金鑰輪替與撤銷流程。既有的自動登入測試不可修改，且必須全數通過。

### 絕對不可發生

- 因目錄寫入失敗或達到上限而讓員工無法登入。
- 公開網站的訪客被寫入目錄。
- 自動建立的帳號因此取得帳密登入資格。
- 一個租戶的金鑰能改動另一個租戶的目錄。
- 登入憑證能拿來同步，或同步憑證能拿來登入。

## 3. 資料模型

目錄項目（`Applicant & { deputyIds? }`）新增下列選填欄位。沒有這些欄位的既有資料視為手動建立，不需要搬移資料。

| 欄位 | 說明 |
| --- | --- |
| `origin` | `manual`（預設）、`sso`、`sync`：建立時決定，之後不再改變。 |
| `syncedAt` | 最後套用的 webhook 事件 `occurredAt`，用於判斷新舊。 |

租戶新增：

| 欄位 | 說明 |
| --- | --- |
| `ssoAutoProvision` | 登入自動建立開關，預設關閉。**（決定）** |
| `directorySyncEnabled` | Webhook 同步開關，預設關閉。**（設計判斷）** |
| `directorySyncKeys` | 同步專用公鑰，與登入的 `publicKeys` 分開存放（§5）。**（決定）** |
| `directoryTombstones` | `{ [userId]: occurredAt }`，記錄刪除事件，防止遲到的舊事件讓人復活；可清除超過 30 天的紀錄。 |
| 最近同步狀態 | 時間與套用／略過／拒絕筆數，供後台顯示。不存個資。 |

`tenantStore.updateTenant`、資料庫 `config` 的欄位對應與 admin 的 `.strict()` schema 都要一併調整。`PUT /users`（整份覆蓋）與 `PATCH` 必須保留 `origin`、`syncedAt`，呼叫端不可自行設定這兩個欄位。

`getApplicant` 目前只移除 `deputyIds`，其餘欄位都會回傳，所以必須同時移除 `origin`、`syncedAt`，否則這些內部欄位會出現在 `/me` 等回應中。

## 4. 登入時自動建立

修改點：`assertionExchange.exchange`（`server/src/modules/auth/assertion-exchange.ts`）。`/api/auth/guest` 不經過這裡，所以免登入訪客不受影響。

當 `ssoAutoProvision` 開啟：

| 目錄現況 | 行為 |
| --- | --- |
| 沒有此人，且無刪除紀錄或登入晚於紀錄 | 建立，`origin: 'sso'` |
| `origin: 'sso'` 且沒有 `syncedAt` | 憑證帶來的欄位與資料不同時，只更新這些欄位 **（設計判斷，見下）** |
| `origin: 'manual'`，或已有 `syncedAt` | 不更新 |

欄位對應沿用 `applicantFromSso`：`name`、`deptName`、`jobPostName`、`companyName`；另外讀取 `email`（格式不合就略過）。**建立時**沒有姓名用 `sub`，沒有部門用 `UNKNOWN_DEPARTMENT`。

**更新只覆蓋憑證實際帶來、且可儲存的欄位：** 沒帶、空白、含 NUL 或單獨代理字元、超過 200 字元的欄位都視為沒帶，保留現值，也不套用上述後備值。否則一張精簡憑證就會把部門打回 `—`，讓此人其他 Session 失去部門角色。

**為何未同步前要由登入更新：** 目錄優先於憑證。若 OA 尚未上線 webhook 就開啟自動建立，員工的部門會停在第一次登入的值，比現在更差。一旦收到第一筆 webhook，就完全改由 webhook 負責。

要求：

- **開關關閉時直接略過：** 不讀目錄、不排工作，以 `exchange` 內一個開關判斷作為唯一新增的分支。
- **不阻塞登入：** Session 建立後才排入背景（例如 `setImmediate`），`exchange` 不等待結果，也不呼叫 `persistCritical`。回傳值與錯誤行為不變。
- **失敗隔離：** 背景工作自行捕捉所有例外。任何失敗或達到 10,000 人上限都只記警告（不含 `sub` 等內容）。
- **尚未寫入時的行為：** 員工的第一個請求可能早於寫入完成，此時走現有的 Session 憑證路徑，得到相同資料。
- 讀取、判斷、寫入要在同一段同步程式內完成（中間不可 `await`），避免同時登入造成資料遺失。
- 資料沒有變動時不寫入。

### 關閉開關

關閉開關必須回到開啟前的行為，否則自動建立的項目不再更新又不能修改，換了部門的人會一直留著舊部門的權限。

- **`getApplicant`：** `origin: 'sso'`、沒有 `syncedAt`，且 `ssoAutoProvision` 未開啟的項目，**本人**改用 Session 憑證（`applicantFromSso`），憑證只帶 `sub` 才退回目錄項目。查別人或背景工作沒有對方的憑證，仍回目錄項目。其他項目不受影響。
- **後台鎖定跟著負責的開關走（`isFieldLocked`）：** 見 §7。
- 帳密登入資格（`isPasswordLoginUser`）只看 `origin`，不受開關影響。

## 5. Webhook 接收端

`POST /api/directory-sync/events`，伺服器對伺服器呼叫，不檢查 `allowedOrigins`。

### 認證

`Authorization: Bearer <JWT>`，使用**同步專用金鑰對**，與登入金鑰完全分開。**（決定）** OA 保管私鑰，HyAgent 只登記公鑰，符合 `docs/HANDOFF-SSO.md`「HyAgent 不持有可偽造身分的秘密」的原則，因此不採用共用密鑰（HMAC）。

專用金鑰的規則：

- **互不通用：** 同步金鑰簽的 JWT 不能登入，登入金鑰簽的 JWT 也不能同步。即使 `aud` 填對，查不到對應公鑰也會被拒絕。
- **不可重複登記：** 公鑰已登記在另一邊時拒絕上傳，否則分開就沒有意義。
- **沿用的規則：** 重用 `tenant-keys.ts` 的 `parsePublicKey`（含誤貼私鑰防護）、`kid` 計算、每組最多 2 把，以及撤銷不可復原。
- **撤銷的影響範圍：** 撤銷同步金鑰只會讓同步停止，不會登出任何人。因此不呼叫 `revokeByKid`，也不套用「最後一把不可在輪替時撤掉」的限制，隨時都能撤銷最後一把。

| 項目 | 要求 |
| --- | --- |
| `alg`、`kid`、`iss`、`iat`、`exp`、`jti` | 與登入 Assertion 相同；`iss` 決定租戶 |
| `aud` | 固定為 `hyagent:directory-sync`，與登入的 `hyagent` 不同 |
| `sub` | 固定為 `directory-sync`（驗證器要求必填）|
| `body_sha256` | 請求原始內容的 SHA-256（hex）|

實作方式：以 `audience` 參數建立新的 `HyAgentAssertionVerifier` 實例，呼叫 `verifyAndConsumeWithKey`，並以 `peekIssuer` 找租戶。

為了不影響登入，實作時遵守：

- **金鑰查詢：** 同步模組自己實作查 `directorySyncKeys` 的 `AssertionKeyRegistry`，不修改 `TenantKeyRegistry`。
- **原始內容：** 同步路由在全域 `express.json` 之前掛上自己的 parser，不修改全域設定。
- **速率限制：** 使用獨立的計數器，大量同步不可佔用登入的額度。
- **時鐘偏移：** 同步請求不呼叫 `recordClockOffset`，後台的自動登入統計維持只反映登入。

重試必須重新簽一張 JWT（新的 `jti`），否則會被防重放拒絕。這點要寫進對接文件。

### 請求格式

```json
{
  "events": [
    {
      "eventId": "evt_01",
      "type": "user.upserted",
      "occurredAt": "2026-11-03T08:00:00.000Z",
      "user": {
        "id": "E1024",
        "name": "王小明",
        "department": "資訊部",
        "title": "工程師",
        "company": "凌網",
        "email": "e1024@example.com"
      }
    },
    {
      "eventId": "evt_02",
      "type": "user.deleted",
      "occurredAt": "2026-11-03T08:01:00.000Z",
      "userId": "E2048"
    }
  ]
}
```

- 每次最多 500 筆事件，完整名單由 OA 分批送。
- `user.id` 必須等於登入憑證的 `sub`，否則同一人會變成兩筆資料。對接文件要強調這一點。
- `user` 是完整資料：沒帶的 `title`、`company`、`email` 代表清除。`name`、`department` 必填。
- `occurredAt` 是資料在 OA 異動的時間，不是發送時間。

### 處理規則

| 情況 | 結果 |
| --- | --- |
| `occurredAt` 不晚於該人的 `syncedAt` 或刪除紀錄 | `stale`，不處理；重送因此是安全的 |
| upsert，此人不存在 | 建立，`origin: 'sync'` |
| upsert，此人已存在 | 更新 OA 欄位並設定 `syncedAt`；保留 `deputyIds`、`region`、`origin` |
| delete | 移出目錄、從他人的代理人名單移除、寫入刪除紀錄、移除此人的個人授權（`accounts`、`accountBundles`）、呼叫 `authSessionStore.revokeBySub`。`userId` 超過 200 字元則 `rejected`（`INVALID_EVENT`）|
| 單筆資料不合法或達到人數上限 | 該筆 `rejected`，其他事件照常處理 |
| `occurredAt` 超過現在 5 分鐘 | 該筆 `rejected`（`INVALID_OCCURRED_AT`），否則此人之後的更新都會被略過 |
| 重送 `occurredAt` 相同的 delete | `stale`，但再次移除個人授權並作廢 Session，避免寫入失敗後重送時離職者留在線上或留著權限 |

**手動建立的同帳號資料：** 由 webhook 接手更新欄位，`origin` 維持 `manual`，所以既有帳密登入資格不變。**（設計判斷）**

**完整名單不會隱含刪除：** 名單中沒出現的人不會被移除，離職一律要發 `user.deleted`。**（設計判斷）** 這是為了避免送錯或送不完整的名單清空目錄。

**離職清除個人授權：** 解析權限時不查目錄（`resolve-scopes.ts`），`accounts`、`accountBundles` 若留著，同帳號復職、或 OA 停止簽發前的一次登入，都會在後台沒顯示的情況下拿回舊權限。復職後部門角色自動生效，個人角色由管理員重新指派。`groups`、`groupBundles`、`tenantBundles` 不動；後台手動刪除也不清（它只是移出目錄，§7 的確認對話框有說明）。**（決定）**

整批事件只寫入一次目錄快照。處理順序固定為：目錄 `persistCritical` → 寫入個人授權清除 → `revokeBySub` → 回 200，任一步失敗回 500，OA 重送時由 `stale` 的 delete 再做一次。

個人授權的寫入不可沿用 `scopePolicy.setPolicy`：它的寫入失敗只記警告，呼叫端也等不到落地（後台權限 API 同樣如此）。所以另有 `scopePolicy.clearAccountGrants`，確定落地才 resolve、失敗則 reject；重試時即使記憶體已清掉也一定再寫一次，否則舊授權會在重啟後復活。

### 回應

| 狀態 | 意義 | OA 的處理 |
| --- | --- | --- |
| 200 | 已處理，`data.results` 列出每筆 `{ eventId, status, reason? }` | `rejected` 的修正資料後再送 |
| 400 | `INVALID_BODY`、`BODY_HASH_MISMATCH` | 修正，不要原樣重試 |
| 401 | 認證失敗，沿用登入端點的錯誤碼與扁平錯誤格式（`toErrorResponse`）| 檢查金鑰與時鐘 |
| 403 | `DIRECTORY_SYNC_DISABLED` | 聯絡管理員 |
| 413 | `TOO_MANY_EVENTS`、`ASSERTION_TOO_LARGE` | 拆批 |
| 429、5xx、逾時 | 暫時性失敗 | 重新簽章後以指數退避重試 |

需套用速率限制（可參考 `auth-rate-limit`）。日誌只記錄租戶、`kid` 與筆數，不可記錄 `sub`、姓名等內容。

## 6. 帳密登入防護

`authService.login` 拒絕 `origin` 為 `sso` 或 `sync` 的帳號，錯誤訊息與帳密錯誤相同。`refresh` 也要做相同檢查，SSO Session 不受影響。**（決定）**

`isKnownUser` 其他用途不變。

## 7. 後台介面

- **新增「人員同步」分頁：** 放兩個開關、同步專用金鑰的上傳／輪替／撤銷與最近同步狀態，操作後立即生效。獨立成分頁是為了不修改 `SsoTab`，也避免管理員把兩組金鑰搞混。金鑰操作的後台 API 同樣另開路由，不修改 `assertion-keys`。
- **使用者目錄（`UsersTab`）：**
  - 顯示來源標記（手動／自動登入／OA 同步）。
  - 姓名、部門、職稱、公司、Email 是否唯讀跟著負責的開關走（`isFieldLocked`）：已有 `syncedAt` 或 `origin: 'sync'` 的帳號只在 `directorySyncEnabled` 開啟時唯讀；`origin: 'sso'` 且沒有 `syncedAt` 的帳號只在 `ssoAutoProvision` 開啟時唯讀；其餘可編輯。後端 `PUT`／`PATCH` 也要拒絕，不可只靠介面擋。介面讀不到開關時，來源不是手動的帳號維持唯讀。
  - 刪除 `origin` 為 `sso`／`sync` 或已有 `syncedAt` 的帳號時，提示「此人再次登入或 OA 再次同步時會重新建立，停權請在 OA 處理」，並說明自動登入的工作階段不會因此結束，要到「自動登入」分頁的「登入 Session」作廢（刪除本身不呼叫 `revokeBySub`）。手動帳號則說明帳密登入的工作階段會失效，同時走自動登入的人不受影響。
- **部門管理（`DepartmentsSection`）：** 提醒有人員但沒有任何角色的部門。因為角色以部門名稱對應，OA 部門改名時，該部門的人會失去角色，這是主要的防護措施。
- 已開啟同步或登入自動建立的租戶，在後台將部門改名或刪除時，要提示下次同步或員工下次登入時可能被蓋回。
- **「人員同步」分頁：** 說明關閉開關後帳號可在使用者目錄編輯，且自動建立的帳號會改回使用登入資料（§4）。

## 9. 已知限制

- **多一把私鑰要管理：** OA 要多保管一把私鑰，也要各自輪替兩組金鑰。對接文件要說明兩組金鑰不可混用，保管方式也要相同。
- **開啟後的資料來源：** 開關開啟後，部門等資料改由目錄提供。登入本身不受影響，但收到 webhook 後，顯示的資料和部門權限會以 webhook 為準，因此兩邊資料不一致時，權限可能和開啟前不同。上線前要依 §11 核對。
- **事件遺失：** HyAgent 不會主動拉取，要靠 OA 重試與定期重送完整名單。漏掉的離職事件不會被完整名單修正，OA 需重送刪除事件。
- **部門改名：** 只有提醒，不會自動遷移角色。
- **多副本：** 目錄存在各副本記憶體，sticky session 部署下其他副本會讀到舊資料。部署文件目前已要求單一副本或 sticky session；啟用本功能的環境應使用單一副本。
- **快照是整個部署共用的：** 目錄存在 `Tenant` 資料的完整快照中，某個租戶開啟同步，寫入的快照涵蓋整個部署的所有租戶資料。若有過期的副本（另一個 replica 的記憶體資料較舊）寫出快照，會把舊資料寫回去，覆蓋剛由 webhook 套用的變更。因此本功能**必須使用單一 replica**，不是建議。
- **寫入成本：** 每次寫入都是完整快照，因此同步端點每批只寫一次；登入自動建立在資料沒變動時不寫。
- **Session 內的資料：** 部門異動下一個請求就生效，因為目錄優先；對話中已經組好的內容不回溯。
- **復職不恢復個人權限：** `user.deleted` 會清除個人授權，復職後只有部門與「所有人」的角色自動生效，個人角色要由管理員重新指派。刪除前後的指派沒有留存可供還原。
- **關閉自動建立後的手動修改：** 帳號變成可編輯，但本人登入時以憑證為準（§4），修改只影響他人查詢與憑證只帶 `sub` 的情況。要讓修改對本人生效，須由 OA 同步接手或改由憑證帶正確資料。
- **離職期間的授權：** 重送相同時間的 delete 時，只要此人仍不在目錄，就會再清一次個人授權，包含管理員在此人離職期間手動指派的部分。

## 10. 驗收條件

**原有自動登入（優先驗收）**
- 既有自動登入測試未經修改，全數通過。
- 開啟後再關閉 `ssoAutoProvision`：本人依憑證判定部門，與開啟前相同。
- 開關關閉時，登入的回應、錯誤碼與 `getApplicant` 結果和改版前一致，且不寫入目錄。
- 開關開啟時，模擬目錄寫入拋錯或寫入緩慢，登入仍立即成功，回應內容不變。
- 此人有刪除紀錄、或資料不合法時，只要憑證有效，登入仍成功。
- `/me` 等回應不含 `origin`、`syncedAt`。
- 大量同步請求觸發速率限制時，登入不受影響。
- 同步請求不影響後台的時鐘偏移統計與 Session 列表。
- 撤銷任何同步金鑰（包含最後一把）後，登入與現有 Session 都不受影響。
- 登入金鑰簽的同步請求、同步金鑰簽的登入請求，即使 `aud` 填對都被拒絕。
- 已登記為登入金鑰的公鑰不能登記為同步金鑰，反之亦然。
- `SsoTab` 與 `assertion-keys` 的行為與改版前相同。

**自動建立**
- 開關關閉時，登入不寫入目錄，行為與現在相同。
- 開啟時，新員工登入後出現在目錄，並取得所屬部門與「所有人」的角色。
- 目錄已滿或寫入失敗時，登入仍成功。
- 免登入訪客不會寫入目錄。
- 自動建立的帳號無法用帳密登入或 refresh。

**Webhook**
- 同一事件重送、亂序送達，結果都與按順序送一次相同。
- 離職後同帳號復職：部門角色生效，個人授權不恢復；政策寫入失敗回 500，重送後清除且已落地。
- 刪除後遲到的舊 upsert 不會讓人復活，較新的 upsert（復職）可以重新建立。
- 離職事件後，該員工現有的 SSO Session 立即失效。
- 登入憑證打同步端點、同步憑證打登入端點都被拒絕。
- 其他租戶的金鑰、竄改過的內容、重複的 `jti` 都被拒絕。
- 一批中有一筆不合法時，其他筆仍套用。
- `deputyIds`、`region` 不會被同步覆蓋。

**後台**
- 負責的開關開啟時，OA 管理的欄位在介面唯讀，直接呼叫 `PATCH` 也被拒絕；開關關閉後可編輯。
- 部門沒有對應角色時會顯示提醒。

**文件**
- 不看 HyAgent 程式碼，只靠 `HANDOFF-DIRECTORY-SYNC.md` 就能發出通過驗證的請求（以文件中的步驟實際跑過一次）。

## 11. 建議上線順序

1. HyAgent 部署新版，開關全部關閉，確認既有租戶不受影響。
2. OA 產生同步專用金鑰對並提供公鑰，依對接文件在測試環境實作，確認憑證帶齊欄位。
3. 測試租戶開啟兩個開關，推送完整名單並驗證，特別檢查部門名稱與後台角色是否對得上。
4. 正式租戶比照辦理：先推完整名單，檢查沒有角色的部門，再開放登入自動建立。
