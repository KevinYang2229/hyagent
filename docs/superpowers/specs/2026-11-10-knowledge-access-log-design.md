# 設計：知識庫 · 敏感文件存取紀錄

日期：2026-11-10
狀態：已確認（2026-11-10），已實作

## Context（為什麼做）

[知識庫 ACL](2026-08-25-knowledge-acl-design.md) 已在檢索時擋住無權的人（pre-filter、fail-closed）。
它回答的是「誰**可以**看」，回答不了出事時被問的「誰**看過**」：

> 薪酬辦法外流了。有權限的 HR 有 12 個人，這兩週誰的問答或報告取用過它？

現況答不出來：

- 問答的 log 只記 `sessionId` 與命中筆數（[`knowledge.agent-service.ts`](../../../server/src/modules/knowledge/knowledge.agent-service.ts)），沒有使用者與檔案。
- 回覆紀錄（`session.replies`）雖帶檢索片段，但每個 session 只留最近 20 則，session 過期即消失；
  只有被評價的那則會進 `reply_feedback`。不是稽核紀錄。
- `auditStore` 綁 `toolId`、每租戶記憶體只保 500 筆，ACL 設計時已否決借用（會擠掉工具稽核）。

## 已確認的決定（2026-11-10）

| # | 決定 |
|---|---|
| 1 | 只記命中**非公開**檔案的取用 |
| 2 | 涵蓋問答、報告、表格、後台試查四條路徑 |
| 3 | 保留 180 天，且要能不改程式、不重新部署即調整 |
| 4 | 第一階段只有平台管理者可查看 |
| 5 | migration 由人工在 Supabase SQL Editor 套用，須早於程式部署 |

## Goals

1. 能回答「某檔案在某期間被誰取用過」與「某人在某期間取用過哪些非公開檔案」。
2. 寫入失敗或變慢**不影響**問答與報告（不改變現行功能）。
3. 紀錄本身不成為新的個資來源：不存問句、回答、檔案內容。
4. 保留期限可在後台調整，到期自動刪除。

## Non-Goals

- 租戶管理者自助查看（第二階段；需要多一層權限）。
- 匯出 CSV、告警（例如「單日取用超過 N 份機密檔」）。先有資料，再看實際需求。
- 記錄網站公開內容、`kb:public` 內容的取用。
- 取代 `auditStore`。兩者語意不同，並存。

---

## §1 「非公開」的定義

**非公開＝網站訪客看不到。** 判定方式：該檔案**目前**的可見性標籤與 `guestVisibilityScopesOf(tenantId)` 沒有交集。

- 不另外維護「哪些標籤算公開」的清單。訪客可見範圍本來就由後台「可見範圍與標籤」決定，
  這裡直接沿用，兩邊永遠一致。
- 標籤取自 `currentChunkScopes`（讀檔案 meta 真相來源），不取 chunk 上的投影，
  與檢索時撤銷權限立即生效的語意相同。
- 網站來源（`file_id` 為 NULL）同一規則：來源的 `audience` 為 `public` 時不記；
  限定部門時要記，`file_id` 留 NULL、`file_name` 記來源網址。

## §2 什麼算「取用」

記**實際交給模型或寫進產出物的內容**，不是檢索候選池：

| 路徑 | 記錄時機 | 理由 |
|---|---|---|
| 問答 `chat` | 重排後實際放進 prompt 的 chunks | 候選池 20 筆大多沒被用到，全記會灌水 |
| 問答 `table` | `loadTable` 載入整張表時 | 表格清單只有表名與欄位名，不算取用內容 |
| 報告 `report` | 各段落實際採用的 chunks、`loadTable` 載入的表 | 報告會彙整成可下載檔，風險高於問答 |
| 後台試查 `admin_test` | `queryTest` 回傳的 hits | 以他人身分試查本身就是可被濫用的能力 |

同一次請求中，同一個檔案只記一筆（多個 chunk、或 chunk 與表格同檔，合併）。

## §3 資料模型

### migration 0021

```sql
create table if not exists knowledge_access_logs (
  id         bigint generated by default as identity primary key,
  tenant_id  text        not null,
  user_id    text        not null,  -- 套用誰的權限（訪客為宿主傳來的 sub，可能為空字串）
  actor_id   text,                  -- admin_test 時為操作的管理者；其他路徑為 NULL
  path       text        not null,  -- chat | table | report | admin_test
  file_id    text,                  -- NULL＝網站來源
  file_name  text        not null,  -- 取用當下的檔名快照；檔案事後刪除仍看得懂
  scopes     text[]      not null,  -- 取用當下的可見性標籤快照
  ref_id     text,                  -- sessionId 或 reportId，供交叉追查
  at         timestamptz not null default now()
);

create index if not exists knowledge_access_logs_tenant_at_idx   on knowledge_access_logs (tenant_id, at);
create index if not exists knowledge_access_logs_tenant_file_idx on knowledge_access_logs (tenant_id, file_id, at);
create index if not exists knowledge_access_logs_tenant_user_idx on knowledge_access_logs (tenant_id, user_id, at);
```

**刻意不存**：問句、回答、chunk 內容、chunk 節錄。問句常含個資（「王小明的考績」），
存了就讓存取紀錄本身成為需要保護的個資庫。要知道問了什麼，以 `ref_id` 回查 session（有其自身的保留政策）。

`file_name`、`scopes` 存快照：檔案改名、刪除、改標籤後，稽核要看的是**當時**的狀態。

### file 後端（開發環境）

記憶體保存，每租戶上限 1000 筆，重啟即清空。讓開發時也走同一套程式，
避免「正式環境才有紀錄」導致呼叫點漏接時沒人發現。

## §4 寫入路徑

### 檢索結果帶出 `fileId`

`KnowledgeChunk` 新增選填 `fileId?: string`。pgvector 兩路查詢的 select 補上 `file_id`；
staticIndex 從 `IndexedChunk.fileId` 帶出；stub 不帶（固定 FAQ，全部視為公開）。

只是多帶一個欄位，不改變檢索條件、排序與筆數。

### 單一入口

```ts
// server/src/modules/knowledge/access-log.ts
recordKnowledgeAccess(
  principal: RetrievalPrincipal,
  path: 'chat' | 'table' | 'report' | 'admin_test',
  items: { fileId?: string; url?: string }[],
  ctx?: { refId?: string; actorId?: string },
): void
```

- **回傳 `void`、不 await**：內部丟進 `DbWriteQueue`，失敗只寫 `logger.warn`。
  呼叫端無法因為它變慢或拋錯。
- 公開判定、合併同檔、取檔名與標籤快照都在這裡做，呼叫端只交出用到的東西。
- 呼叫端不傳 scopes，理由同 ACL 設計（權限資訊不接受外部輸入）。

### 呼叫點

| 檔案 | 位置 | path |
|---|---|---|
| `knowledge.agent-service.ts` | 重排後的 chunks；`loadTable` | `chat`、`table` |
| `report.compose.ts` | 段落採用的 chunks；4 處 `loadTable` | `report` |
| `knowledge.admin.controller.ts` | `queryTest` 的 hits，`actorId` 取管理者 token 的 `sub` | `admin_test` |

`report.outline.ts` 只讀表格清單（表名、欄位名），不記。

**表格在 `loadTable` 內記錄**（實作時調整）：報告的 4 處 `loadTable` 分散在畫圖輔助函式裡，
逐層傳遞參數改動過大。改為 `loadTable(principal, id, path, ctx?)`，`path` 必填——
新呼叫端不選定路徑就編譯不過，與 ACL 設計「改介面讓呼叫端全部編譯失敗」同一個手法。
同一份報告重複載入同一張表，由存取紀錄模組以 10 分鐘窗口合併。

## §5 保留期限

**兩層設定，後台可改：**

1. 平台預設：環境變數 `KNOWLEDGE_ACCESS_LOG_RETENTION_DAYS`，預設 180，範圍 30–3650。
2. 租戶覆寫：`Tenant.knowledgeAccessLogRetentionDays?: number`，平台管理者在後台租戶頁設定，
   **立即生效**，不必重啟或重新部署。未設定時用平台預設。

租戶覆寫放在 `Tenant` 上，是因為平台目前沒有可從後台修改的全域設定表；
新開一張設定表只為一個數字不划算，而不同客戶的法遵要求（例如一年）本來就可能不同。

### 清除

併入 [`index.ts`](../../../server/src/index.ts) 既有的每日排程（與 `feedbackStore.cleanupExpired` 同處）：

- 有覆寫的租戶逐一 `delete ... where tenant_id = ? and at < ?`；
- 其餘租戶一句 `delete ... where tenant_id <> all(?) and at < ?`，以平台預設計算。

開機時也跑一次（停機期間到期的列不會殘留）。刪除租戶時一併清除（加入 `admin.controller` 既有的 `purgeTenant` 串列）。

## §6 後台查詢（平台管理者）

位置：租戶頁 →「知識庫」→「可見範圍與標籤」子頁新增「存取紀錄」卡片，與標籤設定放一起。

```
GET /admin/tenants/:id/knowledge/access-logs
    ?fileId=&userId=&path=&from=&to=&cursor=
→ { items: AccessLog[], nextCursor?: string }
```

- 篩選：檔案（下拉，含已刪除檔名）、使用者、路徑、日期區間。
- 新到舊，游標分頁，每頁 50 筆。游標比照 `feedback.store` 的 `(at, id)`。
- 卡片上方顯示目前的保留天數與「調整」入口（寫 `Tenant.knowledgeAccessLogRetentionDays`）。
- 修改保留天數寫入 `admin-audit`（既有的後台操作稽核），縮短期限會刪資料，必須留痕。

API 掛在既有 `/admin` 路由下，沿用平台管理者驗證，不新增權限概念。

## §7 不影響現行功能的保證

| 風險 | 處理 |
|---|---|
| 寫入拖慢回應 | 不 await，進 `DbWriteQueue` |
| 寫入失敗讓請求失敗 | 例外在佇列內吞掉，只寫 log |
| 檢索結果改變 | 只多帶 `fileId`，SQL 的 where、order by、limit 不變 |
| 程式先於 migration 部署 | 寫入失敗只寫 log（表不存在），問答照常。但仍**應先套 migration** |
| 資料量 | 只記非公開檔、一請求一檔一筆；有界於「非公開檔取用次數 × 180 天」 |

## §8 測試

| 測什麼 | 驗收 |
|---|---|
| 公開檔不記 | 標籤含訪客可見標籤的檔案被取用，不產生紀錄 |
| 非公開檔要記 | 欄位正確：user、path、fileId、檔名與標籤快照、refId |
| 同請求同檔合併 | 同檔 3 個 chunk ＋ 1 張表 → 1 筆 |
| 只記實際採用的 | 候選池 20 筆、重排後用 4 筆 → 只記 4 筆對應的檔 |
| 寫入失敗不影響回應 | DB 寫入拋錯，問答仍回傳正常結果 |
| 四條路徑都有接 | chat、table、report、admin_test 各一案；`admin_test` 帶 `actorId` |
| 網站來源 | audience=public 不記；限定部門時記，`file_id` 為 NULL |
| 保留期限 | 租戶覆寫優先於平台預設；到期列被刪、未到期保留 |
| 刪除租戶 | 該租戶紀錄一併刪除 |
| 不存內容 | 紀錄中不含問句與 chunk 文字（回歸測試，防日後有人「順手」加上） |
