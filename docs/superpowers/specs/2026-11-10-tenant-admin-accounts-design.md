# 租戶管理者帳號與分頁權限設計

日期：2026-11-10
狀態：待使用者審閱

## 1. 背景與目的

後台目前只有一組共用的 `ADMIN_PASSWORD`。登入後拿到的 admin JWT 固定是 `sub: 'admin'`，所有 `/api/admin/*` 都由同一個 `requireAdmin`（`server/src/middlewares/require-admin.ts`）把關，結果只有「是管理者／不是管理者」兩種。因此：

- 後台沒有「個人」的概念，誰登入都能看到並修改**所有租戶**和**所有平台設定**。
- 稽核只能記到「後台密碼登入」加上 IP（`tenant.types.ts` 的 `KeyOperator` 註解寫明了這個限制）。

接下來各租戶會由**客戶指派的一位窗口**自己管理部分設定。這些人是外部人員，不能看到別的租戶，也不能碰平台層設定。開放哪些設定，要由超級管理者決定。

## 2. 目標

1. 新增**租戶管理者帳號**，帳號密碼由超級管理者建立。
2. 每個租戶管理者帳號只屬於**一個租戶**，進不了其他租戶，也進不了平台層頁面。
3. 超級管理者可以替**每個帳號個別**設定租戶分頁的權限，每個分頁三種狀態：**隱藏／唯讀／可編輯**。同一個租戶的不同管理者可以設定得不一樣。
4. 權限在 **API 層**強制把關，前端隱藏或停用只是呈現。
5. 稽核紀錄要能記到「哪一個帳號」做了變更。

## 3. 非目標

- 不做多位超級管理者。超級管理者只有一個人，沿用現有的 `ADMIN_PASSWORD`。
- 不做寄信重設密碼、邀請信、MFA。
- 不讓租戶管理者用租戶自己的 SSO 或前台使用者目錄登入後台。
- 不讓租戶管理者建立或管理其他後台帳號。
- 一個帳號不能跨多個租戶。
- 不做比分頁更細的權限，例如分頁裡的單一欄位或單一按鈕。

## 4. 反目標（做到了也算失敗的情況）

- 只在前端把分頁藏起來，直接呼叫 API 還是能讀或寫。
- 租戶管理者把網址或 API 路徑裡的 `:id` 換成別的租戶 id，就能讀到別的租戶資料。
- 停用帳號或降低權限之後，舊 token 在過期前仍然有效。
- 新帳號一建立就看得到任何分頁。
- 唯讀或可編輯權限能讀到機密原文，例如 AI 金鑰、SSO 簽章相關的秘密值。
- 現有的超級管理者登入方式、`x-admin-key` 機器對機器呼叫、前台功能出現行為退化。

## 5. 角色

| 角色 | 登入方式 | 範圍 |
| --- | --- | --- |
| 超級管理者 | 帳號 `admin`，密碼為 `ADMIN_PASSWORD` | 全部，與現在相同 |
| 機器對機器 | `x-admin-key` header | 全部，與現在相同 |
| 租戶管理者 | 超級管理者建立的帳號與密碼 | 僅限所屬租戶，依分頁權限開放 |

`admin` 是保留帳號名稱，建立租戶管理者時不得使用。

## 6. 已決定的做法

### 6.1 登入

- 登入頁從「只有密碼」改為「帳號＋密碼」。
- 帳號是 `admin` 時，比對 `ADMIN_PASSWORD`。這段沿用現在的 `safeEqual` 和登入限流，簽發的超級管理者 token 和現在相同。
- 其他帳號查詢租戶管理者帳號表，用 bcrypt 比對密碼（專案已經有 `bcrypt` 套件）。帳號停用中或密碼錯誤，都回一樣的錯誤訊息，避免外人藉此判斷帳號是否存在。
- 租戶管理者登入後直接進入自己的租戶頁面 `/tenants/:tenantId`，看不到租戶列表。
- 租戶管理者登入後可以自己修改密碼，修改時要輸入舊密碼。

### 6.2 帳號管理（只有超級管理者能做）

在租戶頁面新增一個「後台管理者」分頁或區塊，只有超級管理者看得到：

- 列表欄位：帳號、顯示名稱、狀態（啟用／停用）、最後登入時間。
- 新增帳號：輸入帳號、顯示名稱、初始密碼。帳號名稱全平台唯一。
- 停用、啟用、刪除帳號。
- 重設密碼，由超級管理者直接設定新密碼。
- 編輯分頁權限：逐一設定每個分頁為隱藏、唯讀或可編輯。

### 6.3 分頁權限

可以設定權限的單位是租戶頁面的分頁（`admin/src/pages/TenantDetailPage.tsx` 的 `TAB_GROUPS`），扣除「總覽」和「資料庫查詢」：

基本設定、AI 模型、自動登入（SSO）、使用者目錄、人員同步、知識庫、表單、角色與授權、外觀、事件通知（Webhook）、用量、回饋、報告、稽核。

**「資料庫查詢」第一版不開放給租戶管理者**（使用者決定）。這個分頁的資料來源掛在 MCP server 上，而 MCP server 的 `ownerTenantId` 可以是 `null`（全平台共用，見 `mcp.store.ts` 的 `belongsTo`），API 也都走平台層的 `/db-intelligence/:serverId/...`。因此權限設定畫面不列出這個分頁，租戶管理者一律看不到，對應的 API 一律 403，之後有需求再另外設計。

**平台欄位只限超級管理者**（使用者決定）：`PATCH /tenants/:id` 裡的月度 token 配額 `quotaMonthlyLlmTokens`，只有超級管理者能改。租戶管理者送出的請求只要包含這個欄位就回 403，畫面上也顯示為唯讀。同一支 API 的其他欄位：`allowedOrigins`、`guestAccess`、`egressPolicy`、`name` 跟著「基本設定」分頁權限走，`appearance` 跟著「外觀」分頁權限走。換句話說，`PATCH /tenants/:id` 要依 body 欄位判斷歸屬哪個分頁，一次請求裡出現的每個欄位都要通過檢查。

規則：

- **新帳號預設全部隱藏。**
- **「總覽」一律看得到**，但只顯示這個帳號至少有唯讀權限的分頁相關內容，總覽背後呼叫的 API 也要依此過濾或拒絕。
- 「表單設計器」頁面（`/tenants/:id/forms/:formId/design`）跟著「表單」分頁的權限。
- **唯讀**：可以呼叫 GET。所有會產生變更或觸發動作的請求（POST/PUT/PATCH/DELETE，包括重新解析、重新生成、撤銷 session、連線測試這類動作）一律回 403。前端對應的按鈕和輸入欄位要停用或隱藏。
- **可編輯**：可以讀，也可以寫。
- **隱藏**：讀寫都回 403，前端不顯示這個分頁。
- **機密欄位**：不論權限多高，租戶管理者都只能覆寫機密欄位，不能讀到原值。清單如下：
  - 租戶自帶的 AI 金鑰（`llmConfig` 裡的各家 API key）：只能覆寫或清除，讀取時只顯示「已設定」或遮罩後的值。
  - API 金鑰 sk_、人員同步金鑰、Webhook secret：**租戶管理者有可編輯權限時，可以自己建立，並在建立當下的回應中看到一次原值**（使用者決定），之後一律只能看到遮罩值。
  - `GET /tenants/:id/webhooks` 目前會回傳 secret 明文（`WebhookTab` 也會顯示），**改成一律遮罩，超級管理者也一樣**。
  - 實作者盤點時如果發現其他機密欄位，照同樣原則處理：讀取只給遮罩值，寫入允許覆寫。
- **一支 API 被多個分頁使用時**（我的決定）：讀取（GET）只要其中任一分頁有唯讀以上的權限就放行；寫入只歸屬於一個主分頁。例如知識庫分頁會讀 `GET /tenants/:id/policy`（主分頁是「角色與授權」），所以「知識庫 唯讀」的帳號也讀得到 policy，但要修改 policy 必須有「角色與授權 可編輯」。對照表的結構因此是「一支端點對應一個寫入分頁、多個可讀分頁」。這代表被隱藏的分頁，資料仍可能透過另一個分頁讀到一部分，這是為了讓分頁本身能正常運作而接受的取捨。
- **稽核分頁**（我的決定）：租戶管理者看得到該租戶的全部稽核紀錄，包括超級管理者和其他租戶管理者的操作，讓客戶看得到平台方對他們設定做了什麼。但只有自己那幾筆會顯示來源 IP，其他人的 IP 一律遮蔽。
- 權限變更、帳號停用或刪除後，**下一個請求就要生效**。

### 6.4 API 把關

- `requireAdmin` 改成辨識三種身分：超級管理者 JWT、`x-admin-key`、租戶管理者 JWT。
  - 租戶管理者 JWT 使用獨立的 audience 或明確的 role，不能被誤當成超級管理者 token。
  - 每個請求都依 token 裡的帳號 id 重新查帳號狀態和權限，不信任 token 裡夾帶的權限，這樣才能做到變更立即生效。實作者可以用短效快取，但停用和權限變更要能讓快取失效。
- 租戶管理者只能呼叫 `/tenants/<自己的租戶 id>/...`。其他租戶 id 和所有平台層路徑（`/tenants` 列表、`POST /tenants`、刪除租戶、`/skills`、`/mcp-servers`、`/scopes`、`/audit`、`/db-intelligence/...` 等）一律 403。
- 需要建立一份 **API 路徑對應分頁** 的對照表，例如 `/tenants/:id/knowledge/**` 對應「知識庫」、`/tenants/:id/llm-config` 對應「AI 模型」。
  - **對照表沒列到的租戶路徑，租戶管理者一律拒絕**（預設拒絕）。這樣之後新增管理端點時，如果忘了登記，就只是租戶管理者打不到，而不會變成漏洞。
  - 需要寫一個測試，列舉 `adminRouter` 上所有已註冊的路徑，確認每一條都有歸屬：屬於某個分頁、只限超級管理者、或是公開路徑。新增端點沒有登記時，測試要失敗。
- 帳號管理 API（例如 `/tenants/:id/admin-accounts/**`）只限超級管理者。

### 6.5 稽核

- `AdminActor` 從 `'admin' | 'admin-api-key'` 擴充成可以記錄租戶管理者帳號，至少包含帳號 id 和帳號名稱。
- `adminAuditTrail` 的每筆紀錄都要帶上操作者。
- 帳號管理的動作（建立、停用、刪除、重設密碼、修改權限）都要留下稽核紀錄，而且**不記錄密碼**。
- 租戶管理者被 403 擋下的變更嘗試照樣記錄（現有的 `adminAuditTrail` 本來就會記失敗的請求）。

### 6.6 資料

- 新增租戶管理者帳號的資料，欄位：id、tenantId、帳號（全平台唯一）、顯示名稱、密碼雜湊、狀態、分頁權限（分頁 key 對應 hidden/read/write）、建立時間、更新時間、最後登入時間。
- 必須同時支援專案現有的兩種儲存後端：`DATA_BACKEND=db` 用 Prisma 新增資料表；file 後端照其他 store 的寫法。
- 刪除租戶時，連帶刪除該租戶的管理者帳號。

## 7. 留給實作者決定

- 帳號名稱的格式規則、密碼強度規則（建議至少 10 碼）。
- 租戶管理者 token 的效期，以及是否需要 refresh token。超級管理者維持現在的 8 小時。
- 權限快取的方式。
- 前端各分頁「唯讀」狀態的呈現方式，例如整區 disabled、隱藏按鈕或加註提示，但整個後台要一致。
- 「後台管理者」要做成獨立分頁，還是放在既有的某個分頁裡。
- 後台頂部列要顯示目前登入的帳號，並提供改密碼和登出。
- 路徑與分頁的對照表放在後端，前端要怎麼取得（例如登入後呼叫 `/me` 取得角色、tenantId、權限）。

- 實作上已知的調整，可以自行處理：
  - `TenantDetailPage` 目前用 `listTenants` 載入租戶資料。租戶管理者不能呼叫租戶列表，所以要新增 `GET /tenants/:id`。
  - 登入請求沒帶帳號時，視為 `admin`，相容舊的呼叫方式。
  - `AdminActor` 從字串改成物件後，`KeyOperator` 的持久化格式要相容舊資料。

## 8. 已知風險與待確認

- **總覽分頁**目前呼叫哪些 API，需要逐一確認並加上過濾。
- 有些分頁會呼叫平台層的 API（例如讀取 skills 或 scopes 清單）來顯示選項。實作者要盤點這些 API，決定是否提供一個限縮過的唯讀版本給租戶管理者。
