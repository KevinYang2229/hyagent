# 上線注意事項：管理後台權限調整（最小權限、角色化、訪客分流）

適用分支：`fix/admin-permission-pitfalls`
讀者：部署人員、租戶管理者、客服／導入人員

本次調整把權限預設改為「最小權限」，並修正幾個容易讓網站訪客取得不該有權限的設定。**部署後既有登入員工的權限不變**，但有幾項行為會改變，部署後請依「部署後檢查清單」逐租戶確認。

---

## 一、行為改變一覽

| 項目 | 之前 | 之後 | 影響對象 |
|---|---|---|---|
| 新建租戶 | 填表申請、知識庫問答、智慧代理與內建表單開給**所有人（含網站訪客）** | 不開放任何能力；預建「通用服務」群組，預設關閉 | 新租戶 |
| 新建表單 | 自動開給所有人（含網站訪客） | 不自動開放，需由管理者加進角色 | 所有租戶 |
| 未指定部門的登入帳號 | 與網站訪客共用「—」的權限 | 獨立的「未指定部門」，與網站訪客分開 | 目錄中沒有部門、或 SSO 未帶部門的帳號 |
| 免登入訪客 Session（`guest_…`） | 會取得「所有登入員工」的角色 | 只取得「所有人」與「網站訪客」的角色 | 開啟 guestAccess 的租戶 |
| 知識庫「測試查詢」留空 | 以管理者帳號查詢（實際等同訪客，但畫面寫「權限最大」） | 明確以網站訪客查詢，並顯示實際身分與可見範圍 | 管理者 |
| 權限儲存 | 整份覆寫，可能蓋掉期間的其他變更 | 帶版本號，期間有人改過會回 409 並提示重新載入 | 管理者、呼叫權限 API 的程式 |
| 權限頁 | 能力為中心的勾選表 | 只有「角色」：每個角色寫明能做什麼與給誰 | 管理者 |

---

## 二、部署時會自動執行的遷移

伺服器啟動時會自動執行，**只跑一次**（以租戶旗標記錄），不需手動操作：

1. **拆分「未指定部門」**（旗標 `unassignedDepartmentMigrated`）
   把原本授權給「—」（網站訪客）的部門授權與角色，**複製一份**給新的「未指定部門」（`__unassigned__`）。遷移後兩邊權限與遷移前相同，之後可分別調整。若新桶已有設定則不覆寫。
2. **舊的直接授權換算成角色**
   不寫入資料庫：權限頁讀取時把舊的「全租戶／部門／帳號」直接授權換算成等效角色（標示「由舊設定轉換」）。管理者在權限頁按一次「儲存」後，才改由角色承載。實際權限在儲存前後都不變。

> 遷移不會刪除任何既有授權，也不會讓任何登入員工失去權限。

## 三、部署後檢查清單（每個租戶）

進入租戶後預設會開啟「總覽」，依其提醒逐項處理：

- [ ] **開放給網站訪客的能力**：總覽若出現此提醒，代表公開聊天視窗的訪客也能使用列出的能力。舊租戶的「全租戶」授權會換算成套用給「所有人（含網站訪客）」的「全體人員」角色——若只想給員工，請在「角色與授權」把該角色的「給誰」改為「所有登入員工」，並檢查直接指派給「網站訪客」的角色。
  - 公開型 App（例如開啟免登入訪客、網站設為所有人可查詢）若需讓訪客使用知識庫問答，請保留或建立一個只含「知識庫問答」的角色給「網站訪客」。
  - 只給訪客知識庫標籤而沒有「知識庫問答」服務時，訪客實際查不到任何內容，公開聊天視窗也不會顯示開場推薦詞。
- [ ] **舊版權限設定**：總覽提醒「舊版權限已換算成角色但尚未儲存」時，到「角色與授權」確認後按「儲存」。可順便替「個別授權：…」這類自動命名的角色改成好懂的名稱。
- [ ] **新建表單**：上線後新建的表單需加進角色（例如「通用服務」），並確認角色含「填表申請」，否則沒有人能使用。
- [ ] **未指定部門**：使用者目錄會列出未指定部門的帳號；他們只取得「未指定部門」與所有登入員工的角色，不會取得一般部門的角色。
- [ ] **新租戶**：建立後到「角色與授權」開啟「通用服務」，或建立角色並套用給部門，員工才有服務可用。

## 四、API 相容性（給呼叫管理 API 的程式）

`GET/PUT /api/admin/tenants/:id/policy`：

- 讀取回應新增 `version`、`memberBundles`（所有登入員工）、`convertedRoleIds`；`grantedScopes`／`groups`／`accounts` 恆回空陣列／物件，舊授權以角色呈現。
- 寫入可帶 `baseVersion`：與目前資料不符時回 **409**（`POLICY_VERSION_CONFLICT`），請重新讀取後再送。不帶則不檢查（相容舊呼叫端）。
- 寫入**沒帶** `tenantBundles`／`memberBundles` 時沿用現有值（已刪除的角色會排除），不會被當成清空。
- `tenantBundles`（所有人）內的角色不可含 `kb:`／`mcp:`，否則回 400。
- 系統保留的部門鍵：`—`（網站訪客）、`__unassigned__`（未指定部門），不可透過部門 API 改名或刪除。

`POST /api/admin/tenants/:id/knowledge/query-test`：未帶 `asUserId` 時以網站訪客查詢；回應新增 `principal`（實際身分、部門、是否在目錄、可見標籤）。

`GET /api/skills`：`roles` 改與實際權限同一套規則，包含「所有人」與「所有登入員工」的角色。

## 五、驗證方式

- 後台「總覽」：必要步驟與提醒是否符合預期。
- 「角色與授權」→「個人權限」：選一位員工與「網站訪客（未登入）」，確認各自最後擁有的能力與來源。
- 「知識庫」→「測試查詢」：留空（網站訪客）與輸入員工帳號各查一次，結果上方會顯示實際身分與可見範圍。

## 六、回復方式

- 權限資料：遷移只新增「未指定部門」的授權，不刪除既有資料；如需還原單一租戶，可在權限頁調整，或以部署前的資料庫備份回復（見 `DEPLOY.zeabur.md` 的「資料庫備份與還原」）。
- 程式：回退到部署前版本時要注意，舊版不認得新的套用對象：
  - 透過「所有登入員工」（`memberBundles`）取得的角色會**失效**，例如「通用服務」，以及改成給所有登入員工的「全體人員」。回退前請先把這些角色改回套用給部門或「所有人」，否則員工會失去這些能力。
  - 「未指定部門」（`__unassigned__`）的授權會被忽略，未指定部門的帳號重新與網站訪客共用「—」的權限。
